# C005 callback-only player input

Historical C005 implementation: its single `onActionTriggered` dispatcher was replaced in [C006](C006-per-action-callbacks.md) by per-action callback methods. Other C005 input behavior remains.

Request (2026-09-26): use one callback path in PlayerInputHandler and add mouse wheel input to the Input System. Preserve existing input timing, cached consumer APIs, UI blocking, action IDs and serialized references.

`PlayerInputHandler` sets its runtime `PlayerInput.notificationBehavior` to `InvokeCSharpEvents` and subscribes once to `onActionTriggered`. It removes its input-polling `Update` and old `InputValue` message methods. The serialized `PlayerInput` setting remains unchanged on disk because the active scene may hold unsaved user edits; runtime code selects the effective behavior. Existing public consume methods remain for PlayerMovement, PlayerInteraction and UI. PlayerInteraction now reads attack press/hold/release only from the handler; it still reads mouse position for pointing.

The handler caches `Move`, `Sprint` and held `Jump` during modal UI but gates their public getters while gameplay is blocked. `GameUIController.RefreshPresentation` clears one-shot input on UI transitions, so held movement can resume after a modal closes without a second key transition. Jump and attack use performed/canceled for press/release. `Interact` has a Hold interaction, so its started phase keeps the previous immediate quick-interaction timing. Inventory remains available while gameplay input is blocked. Roll and tool slots respond on performed. `Player/ToolScroll` is a PassThrough Axis action bound to `<Mouse>/scroll/y`; its performed callback selects the next or previous tool by sign. Existing action and binding entries remain unchanged, and the inputactions asset GUID is retained.

Source and inputactions `.meta` files were unchanged; the PlayerInteraction component GUID was also retained.
